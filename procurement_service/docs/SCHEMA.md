# Database Schema

PostgreSQL, managed via Alembic (`alembic/versions/0001_initial_schema.py`).
All tables use a UUID primary key and `created_at`/`updated_at` timestamps.

## Entity relationship overview

```
vendors 1───* vendor_ledger_entries
vendors 1───* purchase_orders 1───* purchase_order_items
purchase_orders 1───* goods_receipt_notes 1───* grn_items
grn_items *───1 purchase_order_items   (via purchase_order_item_id)
purchase_orders 1───* purchase_invoices (optional; may be null for non-PO invoices)
goods_receipt_notes 1───* purchase_invoices (optional)
purchase_invoices 1───* purchase_invoice_items
vendors 1───* purchase_invoices
```

## Tables

### `vendors`
Master vendor record. `status` ∈ {`active`, `inactive`, `blacklisted`}.
Soft-deleted via `is_deleted` (never hard-deleted, to preserve FK history on
POs/invoices/ledger entries).

### `vendor_ledger_entries`
Append-only. `entry_type` ∈ {`debit`, `credit`}; `source` ∈ {`invoice`,
`payment`, `adjustment`, `opening_balance`}. `balance_after` is a running
balance snapshot computed at write time (debit adds, credit subtracts — see
`API.md`). `finance_service_synced` / `finance_service_ref` track whether
the entry has been mirrored into the Finance Service's ledger; unsynced
rows are retried by the `retry_unsynced_ledger_entries` Celery beat task.

### `purchase_orders` / `purchase_order_items`
`status` enum drives the approval → receipt workflow (see `API.md` for the
full state diagram). `po_number` is a unique, service-generated identifier
(`PO-XXXXXXXXXX`). Money columns are `NUMERIC(14,2)`; `total_amount =
subtotal + tax_amount`, computed server-side from line items, never
trusted from client input.

### `goods_receipt_notes` / `grn_items`
One PO can have multiple GRNs (partial deliveries). Each `grn_items` row
references the specific `purchase_order_item_id` it applies against, and
recording a GRN atomically increments that item's `quantity_received`.

### `purchase_invoices` / `purchase_invoice_items`
`purchase_order_id` and `grn_id` are nullable — invoices can be booked
without a PO (e.g. utility/services invoices). `(vendor_id,
invoice_number)` has a unique constraint (`uq_vendor_invoice_number`) to
prevent duplicate booking. `status` reflects the 3-way match outcome
(`matched` / `disputed`) and downstream payment state.

## Enums (Postgres native `ENUM` types)

| Enum | Values |
|---|---|
| `vendor_status` | active, inactive, blacklisted |
| `purchase_order_status` | draft, pending_approval, approved, rejected, partially_received, received, closed, cancelled |
| `grn_status` | draft, confirmed, rejected |
| `invoice_status` | received, matched, disputed, approved_for_payment, paid, cancelled |
| `ledger_entry_type` | debit, credit |
| `ledger_entry_source` | invoice, payment, adjustment, opening_balance |

## Indexes

Every foreign key column is indexed, plus: `vendors.name`,
`purchase_orders.po_number` (unique), `purchase_orders.status`,
`goods_receipt_notes.grn_number` (unique), `purchase_invoices.invoice_number`,
`purchase_invoices.status`.

## Migrations

```bash
# generate a new revision after changing app/models/*
alembic revision --autogenerate -m "describe the change"

# apply
alembic upgrade head

# rollback one step
alembic downgrade -1
```

Always review autogenerated migrations before committing — Alembic doesn't
reliably detect enum value changes or some constraint renames.
